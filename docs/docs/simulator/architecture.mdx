# Architecture overview

LLMServingSim is two pieces glued together: a **Python serving
frontend** (`serving/`) that does request scheduling, batching, and
trace generation, and a **C++ analytical backend**
([ASTRA-Sim](https://github.com/astra-sim/astra-sim)) that simulates
compute and collective communication on a configurable network.

The Python side is the orchestrator. The C++ side is the
cycle-counting engine that returns elapsed time for each batch.

> This page is the "how it works" overview. If you're looking for
> "how to configure it," see **[Examples](/docs/examples)** instead.

## The two halves

| Layer | Lives in | Talks in | Owns |
| --- | --- | --- | --- |
| **Python frontend** | `serving/` | Requests, Batches, Traces | Scheduling, prefix caching, memory accounting, trace generation |
| **C++ backend** | `astra-sim/` | Chakra `.et` graphs, cycle counts | Compute kernel timing, collective comm modeling, network topology |

They communicate through a single subprocess pipe with a tiny string
protocol, see [Python ↔ C++ boundary](#python--c-boundary) below.

## The 10-step main loop

`serving/__main__.py` drives the simulation. Every iteration of the
loop ticks the simulated clock forward by however many nanoseconds
the next batch takes:

1. **Parse CLI args**: cluster config path, batch parameters,
   routing/expert policies, feature flags
   (`--enable-prefix-caching`, `--enable-attn-offloading`, etc.).
2. **Load cluster topology** via `config_builder`: extracts
   `num_nodes`, instance layout, NPU↔instance mappings, generates
   ASTRA-Sim input files (`network.yml`, `system.json`,
   `memory_expansion.json`).
3. **Initialize per-instance Schedulers and the global Router.**
   Optionally load requests from the dataset.
4. **Spawn the ASTRA-Sim subprocess** (analytical or ns3 backend).
5. **Poll ASTRA-Sim**: `controller.read_wait()` blocks until the
   subprocess says `Waiting`, signaling a completed iteration on some
   NPU.
6. **Route any newly arrived requests** -
   `router.route_arrived_requests(current)` moves requests whose
   `arrival_time_ns <= current` into the appropriate scheduler queue.
7. **Schedule the next batch** -
   `scheduler.schedule(current, sys)` returns a `Batch` (or `None`
   if there's nothing to run).
8. **If we got a batch**: generate the per-layer compute trace
   (`trace_generator.generate_trace`), convert it to a Chakra graph
   (`graph_generator.generate_graph`), and push the graph path to
   ASTRA-Sim (`controller.write_flush`).
9. **DP-group sync** *(optional)*: instances in the same `dp_group`
   defer trace generation until **all** group members have scheduled
   for this iteration, then submit together with a synchronized
   ALLTOALL `comm_size`.
10. **Mark requests done** when ASTRA-Sim reports completion via
    `scheduler.add_done(...)`. The loop exits when every instance is
    idle and there are no pending or deferred requests.

The clock variable is `current` (in **nanoseconds**); converted to
seconds only at output time. Cycle counts come from ASTRA-Sim and add
to `current` on each iteration.

```mermaid
flowchart TD
    START([Start]) --> A[1. Parse CLI args]
    A --> B[2. Load cluster topology]
    B --> C[3. Init Schedulers + Router]
    C --> D[4. Spawn ASTRA-Sim subprocess]
    D --> POLL[5. Poll ASTRA-Sim - read_wait]
    POLL --> ROUTE[6. Route arrived requests]
    ROUTE --> SCHED[7. scheduler.schedule]
    SCHED --> HASBATCH{Got a batch?}
    HASBATCH -->|Yes| TRACE[8. Generate trace + graph]
    TRACE --> DPSYNC[9. DP-group sync if needed]
    DPSYNC --> SUBMIT[Submit to ASTRA-Sim]
    SUBMIT --> ADDDONE[10. scheduler.add_done]
    HASBATCH -->|No| ADDDONE
    ADDDONE --> CHECK{All idle &<br/>no pending?}
    CHECK -->|No| POLL
    CHECK -->|Yes| END([Exit + write CSV])
```

## Python ↔ C++ boundary

There's exactly **one** cross-language boundary: the subprocess pipe
between `controller.py` and the ASTRA-Sim binary.

```mermaid
sequenceDiagram
    autonumber
    participant Sched as scheduler
    participant TG as trace_generator
    participant GG as graph_generator
    participant CTRL as controller
    participant FS as filesystem
    participant ASTRA as ASTRA-Sim (C++)

    Sched->>TG: generate_trace(batch)
    TG->>FS: write trace .txt
    Sched->>GG: generate_graph(batch)
    GG->>FS: write workload .et
    Sched->>CTRL: write_flush(workload path)
    CTRL->>ASTRA: stdin: path
    ASTRA->>FS: read .et file
    Note over ASTRA: simulate compute + comm
    ASTRA->>CTRL: stdout: "Waiting" + cycle count
    CTRL->>Sched: cycle count
    Sched->>Sched: add_done() → metrics
```

Concretely:

1. The Python scheduler decides which requests run this iteration and
   produces a `Batch`.
2. `trace_generator` writes a per-layer text trace to
   `astra-sim/inputs/runs/<run_id>/trace/<hw>/<model>/instance_{i}_batch_{b}.txt`.
3. `graph_generator` shells out to the Chakra converter, producing a
   protobuf graph at
   `astra-sim/inputs/runs/<run_id>/workload/<hw>/<model>/instance_{i}_batch_{b}/llm.et`.
4. `controller.write_flush(process, "<workload-path>")` sends that
   path over stdin.
5. ASTRA-Sim reads the `.et` file, executes the compute + comm graph,
   prints `Waiting <sys=<npu>> id=<batch> cycle=<ns>` on stdout.
6. `controller.read_wait` parses that line; the main loop hands the
   cycle count to `scheduler.add_done` to update request metrics.

The protocol is just three commands on the Python → C++ direction:

- A workload path, start running this batch.
- `pass`: re-poll without computing (used during DP-group sync waits).
- `done`: this instance is idle.
- `exit`: shut down.

There is no shared memory, no callback API, no FFI, only files and a
text protocol. Adding a new feature on the Python side rarely
requires touching C++ as long as the trace fields the converter knows
about are sufficient (see
[Reference → Trace file format](/docs/reference/trace-format)).

## What state is shared, and where it lives

A few cross-module pieces of state are worth knowing about because
they show up in multiple pages:

- **`Router._pending_requests`**: requests loaded from the dataset
  but whose `arrival_time_ns` is in the future. Sorted by arrival.
- **`Router._deferred_sessions`**: agentic sessions waiting on a
  tool call to elapse before releasing the next sub-request.
- **`Scheduler.memory: MemoryModel`**: per-instance NPU + CPU
  memory tracker, including the per-instance NPU prefix cache.
- **Shared CPU/CXL `RadixCache`**: second-tier prefix pool. Optional
  (`--enable-prefix-sharing`); when enabled, all instances on a node
  share one tree.
- **`dp_pending` (in `__main__.py`)**: per-DP-group barrier dict
  used to coordinate wave-synchronized trace submission.

Each of these is explained in the page that owns it; this list is
just so you have a map when something cross-references.

## Modeled serving metrics

The simulator prints `SIM_METRICS` while a run is active and a
`SIM_METRICS_SUMMARY` line before it frees simulated memory. These are
modeled values derived from scheduler state and emitted traces, not DCGM,
NCCL, or vLLM telemetry from physical GPUs.

`kv_cache_util` is current modeled KV occupancy:

```text
currently allocated KV bytes / modeled KV capacity
```

`kv_pressure_score` is a capacity-planning ratio. It uses every waiting or
in-flight request's requested final context length, block-rounds each request
through the model's KV layout, and divides the resulting demand by modeled KV
capacity. Values above `1` mean the requested workload exceeds that capacity.
The final summary reports the maximum value seen during the run as
`kv_pressure_score_peak`.

`per_tok_comm_bytes` is modeled per-rank wire traffic divided by all scheduled
prefill and decode tokens:

```text
(TP/EP collective ring traffic + modeled PP activation handoffs)
/ scheduled prefill and decode tokens
```

Its unit is bytes per scheduled token. It is not decode-only and is not a
physical NVLink or PCIe TX/RX counter. The value is `N/A` until the instance
has generated at least one batch trace.

`output_length_observed` is the average generated length of generation
requests completed during the current simulator reporting window:

```text
delta(output_tokens_sum) / delta(completed_generation_requests)
```

For each completed generation request, the simulator adds
`req.output - req.original_input` to `output_tokens_sum`. Prefill-only
instances and encoder models report `N/A`. In P/D mode, the request is counted
on decode completion, not when prefill transfers it to the decode instance.

This is exact under simulator semantics, but it is not sampled EOS behavior:
the workload supplies the requested output length in advance, and the
simulator does not currently model early EOS, cancellation, or
sampling-dependent output lengths.

`input_length_observed` is the average original prompt length of requests
completed during the current reporting window. Prefix-cache hits do not reduce
the observed length. In P/D mode, requests are counted only at terminal decode
completion so they are not counted once by each pool.

`prefill_iteration_counts_per_second` and
`decode_itr_counts_per_second` count completed real scheduler batches over the
simulated reporting-window duration. A mixed batch increments both counters.
Chunked-prefill batches count once per completed chunk, while DP dummy batches
are excluded. Decode detection uses the real `decode_k_list`, which is not
modified by DP padding.

`comm_overhead_pct` is a fraction in `[0, 1]`, despite the `_pct` suffix:

```text
sum(per-NPU communication-active cycles)
/ sum(per-NPU workload elapsed cycles)
```

ASTRA-Sim measures union-active communication time for collectives and native
sends/receives. Compute overlap is not added to the numerator, and memory/PIM
operations are not classified as communication. This is communication
occupancy, not the counterfactual latency reduction from making communication
free.

For PP configurations, `pipeline_bubble_fraction` is the cumulative modeled
NPU-rank idle-capacity fraction:

```text
1 - sum(per-NPU compute-or-communication-active cycles)
    / sum(per-NPU workload elapsed cycles)
```

ASTRA-Sim reports every managed PP rank, including middle stages. Compute and
communication overlap is counted once through a union-active counter. The
metric includes any rank idle time during a workload, so it can reflect
fill/drain bubbles, stage imbalance, dependency stalls, or memory waits; it is
not a causal attribution to fill/drain alone. `pp_size=1` reports `0`.

Each rank emits its timing when its own iteration completes. The simulator
aggregates an instance metric only after it has one report from every rank for
that instance and iteration.

The current supported system assumes `EP=1` and no P/D split. Consequently,
`expert_inbalance` and `pd_inbalance` are temporary constants of `0`, meaning
perfectly balanced/not applicable under those assumptions. They must be
replaced with routing-count and per-pool-utilization calculations before EP or
P/D configurations use these fields.
